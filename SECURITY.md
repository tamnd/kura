# Security policy

## Reporting a vulnerability

Please report vulnerabilities privately through [GitHub Security Advisories](https://github.com/tamnd/kura/security/advisories/new). Do not open a public issue for a security problem.

Include what you found, how to reproduce it, and what an attacker gets out of it. A proof of concept helps a lot, and for this project a byte string that makes a decoder misbehave is the best possible one. You will get an acknowledgement within three working days and an assessment within seven.

## Supported versions

The latest tagged release is the supported one. Fixes are released as a new patch version rather than backported.

## What counts as a vulnerability here

This engine reads bytes that came off a disk or across a network, and it is linked directly into a host process. That makes the decoders the attack surface, so anything a crafted input can do to them counts:

- A panic, an abort or an out of bounds read from any decoder on any input.
- A read past the end of a buffer, an integer overflow that becomes a length, or an allocation sized from an untrusted value.
- A use after free, a double free or a leak reachable through the C ABI when the documented contract is followed.
- A panic that unwinds across the FFI boundary.
- A decoder that accepts an input the encoder could not have produced and returns a value the caller then trusts.
- Anything that lets one caller's data appear in another caller's result, including through a shared buffer that was not cleared.

Bitmaps carry a reader's visibility through a query, so a bug that adds an identifier to a set is a permission bug wherever this engine is used, not just a wrong answer. Treat it that way.

## What does not

- Misuse of the C ABI against its documented contract, such as freeing a buffer twice, passing a handle from another thread while it is in use, or passing a length that does not match the pointer. These are documented as caller obligations because there is no way to check them at the boundary.
- Resource use that is proportional to the input. A large file takes a large amount of memory to decode.
- Reports generated by a scanner with no analysis of whether the finding is reachable.

## Release integrity

Release checksums are signed with cosign using keyless signing. To verify a download:

```sh
cosign verify-blob checksums.txt \
  --certificate checksums.txt.pem \
  --signature checksums.txt.sig \
  --certificate-identity-regexp 'https://github.com/tamnd/kura/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```
